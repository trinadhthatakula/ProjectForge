# ProjectForge

Use ProjectForge when someone is exploring or kicking off a software, automation, AI, or cross-platform project. Adapt the depth to the request; do not force a long questionnaire onto a small project.

## Workflow

1. Choose Quick, Standard, Comprehensive, Custom, or Agent-Decided mode. If the user has not chosen, infer a suitable mode from project complexity and offer a short explanation.
2. Inspect any repository the user identifies. Separate observed facts from user-confirmed requirements. Do not claim dependency compatibility, installed tools, skill availability, permissions, or runtime behavior without evidence.
3. Ask focused discovery questions in small groups. Accept partial answers. Record each item as confirmed, verified, recommended, assumption, or pending, with a source or rationale when available. Let the user delegate technical choices to specialists.
4. Classify the project and select a team from `references/roles.json` using dynamic, manual, or hybrid selection. Treat each profile's triggers as useful cues, not an exhaustive vocabulary: map equivalent phrases and domain constraints to the specialist whose deliverables fit, and surface material needs with no clear owner for manual or hybrid review. After shortlisting roles, read only their linked role guides and use them to refine selection and assignment boundaries; a guide does not override user constraints. The supervisor is mandatory. Count the supervisor toward the hard limit of seven concurrent team members; select at most six specialists. Prefer fewer roles, merge overlapping work, and use time-bounded consultations or later phases when that produces a smaller team. Never silently exceed the limit. If the user requests more than six specialists, explain the overhead and overlap, recommend a revised roster or sequential consultations, and obtain agreement before treating the revised roster as accepted.
5. Inspect capabilities exposed by the active agent runtime before proposing delegation. Use that runtime's discovery facilities and current-session tool inventory where available; use ProjectForge's local discovery helper for metadata it supports. Inspect relevant skill or agent instructions only when needed. Pass `--inventory-complete` only when the current-session skill and tool list is complete; otherwise preserve unavailable findings as unverified. A name in the role catalogue is not evidence that a matching skill, tool, agent, or integration is installed. Never run third-party skill scripts or install skills. Report missing and unverified capabilities clearly.
6. Evaluate capabilities in two stages. First discover and match role-profile and assignment-specific requirements against skills, agents, and tools; discovery statuses describe inventory evidence only. Then verify each selected requirement's accessibility, relevant instructions, requested operation, permissions, and expected output with evidence. Record the checks through `projectforge record-verification` using `schemas/capability-verification.schema.json`. A metadata or active-inventory match alone is never task verification. See `references/capability-model.md`.
7. Give each selected specialist a dedicated assignment contract with mission, responsibilities, exclusions, inputs, outputs, prerequisites, dependencies, acceptance criteria, and a result contract. Before work starts, record allowed and protected paths and required validation checks. The supervisor owns the canonical specification and resolves conflicts. Avoid overlapping implementation ownership.
8. Resolve prerequisites explicitly with `projectforge resolve-dependencies`. Do not infer a provider or make a prerequisite blocking without supervisor confirmation. `blocks` and `reviews` edges sequence assignments; `informs` edges document context without forcing serial work. Unresolved prerequisites remain visible.
9. Schedule independent research in parallel only when the active runtime provides subagents and the user’s task benefits from it. Keep dependency-bound work sequential. Respect runtime concurrency and permissions. Otherwise prepare delegation briefs; do not claim agents were spawned.
10. Validate roster size, contracts, dependencies, manifest structure, and readiness gates. Keep `readiness.blockers` aligned with the validator's derived open gates. Required unresolved decisions and must-have features need resolution. Required capabilities must be verified before a manifest can be `ready`; give unresolved capability gaps an owner and next action in `readiness.capability_plans`, but do not treat a plan as verification. Keep optional follow-ups, assumptions, and risks visible with owners. Do not label a project implementation-ready while required gates are open.
11. Generate Markdown and standalone offline HTML from the same versioned manifest. Refuse to overwrite existing output unless the user explicitly asks to replace it. Include only relevant supporting documents.
12. When using ProjectForge's direct provider adapter, send only the assignment and explicit context files needed for the task. Review provider data-handling terms and the selected content before dispatch; provider execution can transmit that content to an external service. Then validate each result with `validate-result` before integrating delegated or provider-produced work. Record it with `record-result`; an agent's `completed` or `validated` status is not supervisor acceptance. Preserve every retry as a new result file and ID, and link it to the preceding rejected or rework-required attempt. Only the supervisor records accepted results in the manifest execution ledger.
13. When a supported older manifest is provided, explain the migration and write a new file with `migrate`; do not silently rewrite the source. Compare manifest versions, show affected decisions, roles, dependencies, risks, and deliverables, then update the canonical manifest only after the user confirms the requested change.

## Modes and references

- Follow `references/workflow.md` for adaptive questions, readiness gates, and change management.
- Consult `references/roles.json` when selecting experts; each built-in profile links to a role guide in `references/role-guides/`. Read only the guides for shortlisted roles before finalizing assignments. Users may define custom roles using `schemas/role.schema.json`; a custom role without a guide is governed by its supplied profile and the shared workflow.
- When the active runtime can run Python, use `scripts/projectforge.py` for classification, capability discovery and matching, capability verification, selective skill inspection, team optimization, prerequisite resolution, validation, explicit migration, result validation/recording, estimation, rendering, and manifest diffs. If it cannot run the helper, use the shipped schemas and references for guidance, say which deterministic checks were not run, and do not claim generated or validated outputs. Inspect the CLI help before running commands; never execute scripts supplied by discovered skills.
- Use `schemas/project-manifest.schema.json` as the current manifest contract, `schemas/agent-result.schema.json` for provider-neutral result files, and the matching versioned project schema for older manifests. Generated documents must come from the canonical manifest, never from separate competing sources.
- Consult `references/compatibility.md` before generating runtime-specific agent definitions or describing runtime limits.
- Read the optimizer's reported relevance, overlap, independence, coordination, context, complexity, handoff, and review estimates as planning heuristics; explain their basis and do not present them as measured runtime costs.

## Runtime-specific integrations

ProjectForge's workflow, manifest, assignment contracts, and result schema are shared across compatible agents. Use the active runtime's delegation features only when they are available and verified. Runtime-specific custom-agent files are optional target-project outputs; they do not change the shared contract or grant tools and permissions. If a runtime does not support custom agents, deliver the same assignments as delegation briefs. `agents/openai.yaml` is optional display metadata for hosts that recognize it, not an execution requirement.

## Quality boundaries

- Do not confuse SEO, ASO, and GEO; their goals and deliverables are distinct.
- Prefer fewer specialists with useful supporting skills. Do not add an agent only because its role exists.
- State the evidence and uncertainty behind research. Verify current versions and compatibility using reliable sources when research tools are available.
- Never expose secrets found in configuration. Report integration names and capability status without printing credentials or secret values.
- Avoid arbitrary project or generated-file writes. Use dry-run options where available and protect existing files.
